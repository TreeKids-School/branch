# 通信エディターと入力設定の再監査

調査日：2026-10-05。対象は `ツリー通信v2/src/` のソースと前回の画像モック12枚です。現行 `branch/src/` は参照専用とし、この調査ではアプリや業務データを変更していません。以下はコードからの到達性・条件の確認であり、実利用者による操作検証の完了を示すものではありません。

## 調査対象と判定方法

- 主なソース：`App.jsx`、`components/MemoPanel.jsx`、`components/SettingsModal.jsx`、`components/LogModal.jsx`、`utils/greetingUtils.js`。
- 画像の照合対象：前回の M03・M04・M05・M06・M07・M08・P03・P04。前回12枚全体の役割は README・DESIGN-NOTES でも確認しました。
- 「到達可」は App から UI のイベントへつながること、「条件付き」はデータや状態に応じて現れること、「未接続」は関数・コンポーネントが存在しても通常 UI から呼ばれないことを意味します。
- 予約内で動く通信V2は利用者別のブラウザー内仮保存です。共有サーバー、旧通信データの移行、予約からの児童・日付・事業所の自動引継ぎは未接続です。ロック・競合のコードがあることを、現在の別スタッフ間共有が動作する根拠にはしません。

行番号は調査時点の `ツリー通信v2/src/` からの相対パスです。アプリ改修により変わるため、併記した関数名も参照してください。

### 共有タグは分類だけではない

`【共有】`付きのメモ投稿は施設の共有事項へも追記されます。この作用を隠して「タグの色分けだけ」に再構成しないこと。短い説明は「このメモは共有事項にも追加されます」とします。

現在のメモ編集・削除処理は、追記済みの `globalLog.activities` を逆に更新・削除しません。「共有事項も同時に更新される」とは表示できません。将来この挙動を変えるなら、投稿と転記の識別・履歴を設計する別の改修です。

## 3. 今回の担当画像に必ず残す項目

### P08 通信本文・今後の予定・名前警告・完了解除

- 予約V2の外枠、通信側の事業所・日付・児童、ブラウザー内仮保存・未共有の境界。
- プレーンテキストの通信本文。太字・斜体・リンクなど未実装の編集ツールを置かない。
- 「ツリー通信」「今後の予定」の区別と、メモからの反映。
- 名前の可能性がある箇所と「名前が含まれている可能性があります」。万能な個人情報検査や自動匿名化をうたわない。
- 「入力完了済み」「完了を解除」「保存して閉じる」。解除を公開取消やLINE送信取消と呼ばない。
- 挨拶・プログラム・メモから反映の入口。担当者の表示。

### M13 今後の予定

- 児童・事業所・日付と「本文へ戻る」。本文とは別の編集対象であること。
- 「参考メモ」「予定へ反映」、入力欄、文字数と「80文字は目安」。架空例は「次回も色紙を選ぶところから始め、本人のアイデアを聞く。」。
- 「このブラウザーに仮保存」「保存して閉じる」。端末をまたぐ共有・確定予約の自動反映と誤解させない。

### P09 / M14 タグ・定型文設定

- 「挨拶」「タグ・定型文」「OKワード」のタブ。
- タグ名、挿入文、プログラム内容を入れる設定、表示列、追加・削除、保存・取消。
- 架空例：タグ「【制作】」、挿入文「制作では、」、表示列「プログラム」。プログラム差込み用には `{プログラム内容}` を用いる。
- スマホは一つのタグを縦に編集し、横長設定表を縮小しない。
- `【共有】`には「共有事項にも追記」の説明を残す。

### M15 挨拶・OKワード

- 挨拶対象のスタッフ選択、複数行本文、「この挨拶を保存」。架空例は「こんにちは、スタッフAです。本日のツリー通信です。」。
- OKワードの一覧、追加、削除。「名前チェックから除外する言葉」と説明する。
- 一時的な無視ではなく保存される除外設定として扱う。実名の誤検出を無条件に除外するよう誘導しない。
- スタッフ切替と編集状態を見失わない。挨拶保存とタグ等の全体保存を混同しない。

### P14 / M20 競合比較案

- 表示上で「共有接続時の比較画面案」と分かるようにする。現在のスタッフ間共有が完成したという見せ方を避ける。
- 「別の保存内容が見つかりました」「編集中の内容」「保存済みの内容」を分ける。
- 架空の短い差分例：手元「青い色紙を選び、一枚ずつ貼っていました。」／保存側「青い色紙を選び、貼る位置を考えていました。」。
- 各本文を確認して「自分の内容を残す」「保存済みの内容を取り込む」。単一の曖昧な「続行」にはしない。
- コピー・入力完了を無効にした状態を示す。PCは左右比較、スマホは縦比較で文章を省略しすぎない。
- ロック中の一覧と競合比較は別状態。競合が出れば共有・安全制御が全て動作済みとは判断しない。

### P15 / M21 メモ編集・複数プログラム差込み

- 時刻と投稿者、編集対象の本文、複数タグ、保存・取消。
- 複数プログラムの名前・担当・内容、個別選択、「すべて挿入」「文字挿入なし（タグのみ）」。
- 内部メモであること、`【共有】`による施設共有事項への追記を明示する。
- スマホでも編集・削除操作を hover 前提にしない。

## 4. 台帳の訂正と未接続コード

1. 初期の `CURRENT-ARCHITECTURE.md` にある「履歴から復元」「全員コピー」は、有効 UI としての記述が過大でした。`LogModal` は `onRestore` を受け取らず旧値コピーのみ。全員コピー関数に UI 呼出しはありません。前回 `FUNCTION-COVERAGE.md` はこの区別を既に記載しています。
2. `DocViewer` は描画ブロックがありますが、`setSelectedDocChildId` は宣言と `null` への設定だけで、通常 UI から到達できません。閲覧・編集・個別印刷の再接続は別の実装です。支援記録のフィールドや出力処理があることと、編集画面が有効であることを分けます。
3. `handleSort` は残っていますが、UIからの呼出しを確認できません。現在の時刻順表示と利用者による手動の並べ替えを混同しないこと。
4. `TreeCommPanel`、本文内のテンプレート編集用 state、予定コピー用 state も未使用です。設定画面の挨拶編集は有効です。
5. `LogModal` の見出しは「直近100件」ですが、表示コードは `filteredLogs.map` で、100件に制限する処理を確認できません。
6. メモの自由な定型文は接続済みです。`App.jsx:3680` が `tagInsertTexts` を渡しています。

## 5. 実装時に確認する境界

- 現行の名前検出は敬称付き語の正規表現であり、全ての実名や個人情報の検査ではありません。
- OKワードの警告ボタンは「一時的」と表示しますが、実装は保存される設定です。新案では作用を正確に書きます。
- 競合時に下部のコピー・保存・完了は無効ですが、上部の×は `handleClose` に直結しています。全ての離脱経路が安全と断定しないこと。
- `futurePlan` には下書き保護表示がある一方、ローカル下書き JSON の対象は本文・入力中メモ・選択タグで、予定は含みません。保存失敗時の保護範囲を確認します。
- 設定保存や完了操作の一部は呼出し完了を待たず UI を閉じる構成です。モックの「保存しました」を表示する時点は、実装時に成功結果と合わせる必要があります。
- 結合コピーは現行では姓に基づきます。姓の一致を家族 ID や LINE 送信先の確定とみなさないこと。
- 「入力完了」「コピー成功」「手動送信確認」「予約V2での保護者公開」は別の状態です。AIバディ、写真、LINE自動送信は今回の補完画像の範囲外です。
