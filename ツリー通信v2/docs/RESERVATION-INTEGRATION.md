# 予約V2との連携設計

調査日：2026-10-04

この資料はローカルのソースコードを読み取った結果と、今後の連携案をまとめたものです。実データ、実環境の動作、現在の配備内容は確認していません。ここに記載した連携は未実装です。

今回のツリー通信V2は、既存システムと切り離したエミュレーター環境で構成を整理する段階です。既存Firebaseへの接続、実データの取込み、AI APIの実行、LINE送信は行いません。

## 1. 守る境界

- 既存ツリー通信システムのコード・設定・データを変更しない。
- 予約V2の児童、予約、既存下書き、公開本文を、この段階では変更しない。
- 新しい通信V2に既存の認証情報や実データをコピーしない。
- 将来の連携も、まず読み取り専用の取得から開始し、取込候補、確認済み下書き、保護者向け公開を分ける。
- 既存のデータが消えたことを理由に、連携先を自動削除しない。逆方向の書き戻しも行わない。

## 2. 既存通信システムのデータ構造

保存処理の主な根拠は [useStorage.js](../../branch/src/hooks/useStorage.js)、日別と児童別への保存呼出しは [App.jsx](../../branch/src/App.jsx) にあります。

| 保存先 | 内容 | 連携上の扱い |
| --- | --- | --- |
| `reports/{officeId}_{YYYY-MM-DD}` | 日別の児童一覧、通信本文、メモ、日表、全体記録 | 通信の取込元候補。旧形式として日付のみの文書IDも存在するコード構成 |
| `results[childId].D` | 児童別のツリー通信本文 | 原文として保持する |
| `results[childId].futurePlan` | 今後の予定 | 本文とは別項目。公開の可否を個別に設計する |
| `results[childId].isCompleted` | 通信の入力完了 | 公開済み・LINE送信済みとは解釈しない |
| `children/{childId}/app_categories/書類管理/tree_communications/{date}` | `tree_comm_text`、`future_plan`、送迎等の項目を持つ児童別の写し | 日別記録との照合候補。これだけを唯一の正本にはしない |
| `meta/reports_index_{officeId}` | 事業所別の日付一覧 | 取得範囲の候補。網羅性は別途確認が必要 |
| `daily_reports` | `childId`、`date`、`externalInfo`、`staffName` 等 | 別種の記録。通信本文の保存先と混同しない |

`reports` には `children`、`messages`、`results`、`summaryC`、`dailyTable`、`globalLog`、`changeLogs`、`updatedAt` が保存されます。職員のメモや全体記録まで保護者向け本文へまとめて取り込まないことが必要です。

### 確認できた注意点

1. 児童別の `tree_communications/{date}` には、現在の保存呼出しでは `officeId` と `isCompleted` が渡されません。同じ児童・同じ日で複数事業所が書くと、保存先が衝突する可能性があります。
2. 日別記録と児童別の写しは、別々の保存を `Promise.all` で待つ構成です。二つが常に同時に成功するトランザクションではありません。不一致時には自動でどちらかを正しいものと決めません。
3. `updatedAt` は日別全体の変更や一括保存でも更新されます。本文が変わったかの判定には、その児童の連携対象項目のハッシュを使用する設計が必要です。
4. `isCompleted` の操作は [MemoPanel.jsx](../../branch/src/components/MemoPanel.jsx) の「入力を完了して保存」です。保護者への公開承認やLINE送信結果の記録ではありません。
5. `useStorage.js` はFirestore操作に失敗するとローカル保存へフォールバックします。通信V2では、端末保存とサーバー保存を区別して表示する必要があります。
6. 今回確認した `src` 内では、写真アップロードや写真の保存先を特定できませんでした。写真を既存データから取得できることは未確認です。

## 3. 予約V2に存在する機能

以下はコード上の機能一覧です。今回、配備先での実動作は確認していません。

| 下書きと公開 | 下書き保存、保存済み本文の公開・非公開、公開本文の更新 |
| 一括公開 | 当日分の対象を確認し、選択した記録を順に公開・非公開 |

### 現行の保存モデル

- `communicationDrafts/{reservationId}`：職員向けの下書き。
- `publishedCommunications/{reservationId}`：保護者向けの公開本文。
- `communicationAudit`：職員向けの変更履歴。下書き本文を含む。

下書きは `reservationId`、`childId`、`facilityId`、`businessDate`、`body`、`revision`、`updatedAt`、`updatedByUid` を持ちます。公開記録は対応する本文と `draftRevision`、`publishedAt` を持ちます。

本文は20,000文字以内です。現行の下書き保存APIは `reservationId` と `body` を受け取り、追加の未知フィールドを拒否します。写真、バディ文、取込元ID等を、そのまま既存APIに追加して送ることはできません。

### 認証と公開範囲

予約V2では、Firebaseへのログインだけでは書込権限になりません。サーバーが管理するactiveのmembershipと事業所権限を確認し、Callableを介して保存します。ブラウザーからの業務文書への直接書込は許可されていません。

下書きと監査履歴は職員向けです。保護者が読める公開記録は、activeのmembershipと、その児童へのactiveの `guardianLinks/{uid}__{childId}` によって限定されます。連携元のログインUIDが予約V2でも同じ権限を持つとは仮定しません。

根拠：[Firestoreルール](../../../tree-kids-schedule/V2/firestore.rules)、[membership](../../../tree-kids-schedule/V2/shared/domain/membership.ts)、[コマンド実行基盤](../../../tree-kids-schedule/V2/functions/src/runtime/commandRunner.ts)。

## 4. 既存のCSVで接続できる範囲

通信システムの [CSV出力](../../branch/src/utils/export.js) は、`児童名`、`日付`、`ツリー通信` の列を出力します。この列構成は予約V2の取込処理で扱えます。最初の接続検証は合成データのCSVで行えます。

ただし、現行CSVには永続的な連携用の児童IDがありません。予約V2の現行照合は氏名の正規化と日付・事業所・確定予約で候補を探すため、同名、改姓、表記差、対象外事業所、予約未登録を解決できない場合があります。

現行取込は新規下書きを最初に選択し、既存下書きの置換には比較と選択を求めます。公開本文は変えません。この分離を自動連携でも維持します。定型挨拶の除去は任意の加工とし、原文を別に保持します。

## 5. 安定した識別子と差分判定

今後設計する取込候補は、少なくとも次の情報を持つ想定です。以下は提案であり、現行フィールドではありません。

| 項目 | 目的 |
| --- | --- |
| `sourceSystem`、`sourceProject` | 取込元システムを識別 |
| `sourceReportId`、`sourceChildId`、`sourceOfficeId` | 元の記録・児童・事業所を識別 |
| `businessDate` | 通信が対象とする業務日。取込日とは分ける |
| `rawBody` | 取得した原文を保持 |
| `sourceHash` | その児童の連携対象項目の内容を比較 |
| `sourceUpdatedAt`、`fetchedAt` | 元の更新日時と取得日時を区別 |
| `targetChildId`、`targetFacilityId` | 確認済みの対応付け |
| `targetReservationId` | 対応する確定予約がある場合のみ保持 |
| `importStatus`、`lastImportedHash`、`targetRevision` | 未照合、下書き候補、競合、保存済み等の進捗を管理 |

児童の対応付けは `sourceSystem + sourceProject + sourceChildId` を基準に、職員が予約V2の `childId` と確認して保存します。事業所も同様に対応付けます。氏名は確認材料であり、永続キーや自動確定の根拠にはしません。

取込元レコードのキーには事業所と業務日を含め、内容ハッシュとは分離します。同じ通信を再取得したときは同じ元レコードとして扱い、内容が変わった場合は新しい候補版を作ります。ハッシュ計算に日別全体の更新日時、取得日時等を含めません。ハッシュ方式と正規化方法はバージョン管理します。

予約V2へ保存する際は既存の `expectedRevision` とコマンドIDによる再送処理を使用し、原文が同じ場合は再保存しません。元の通信と予約V2側の下書きが両方編集されていたら、差分確認に戻して自動上書きを止めます。

## 6. 段階的な接続

### 段階A：独立した開発環境と合成データ

通信V2の保存先を既存環境から分離します。既存業務の画面・保存形式・入出力を把握し、合成データで画面と取込候補の構成を検討します。今回の範囲です。

### 段階B：読み取り専用の取込候補

将来、接続先と対象範囲を確定したうえで、サーバー側に読み取り専用の取得経路を設けます。取得した本文は通信V2の取込候補に保存し、旧システムのデータ・完了状態・索引には書き戻しません。

不明な児童、事業所の不一致、日別記録と児童別の写しの不一致は確認待ちにします。取得の成功を公開の成功とは扱いません。

### 段階C：照合済みの下書き取込

職員が児童・事業所・日付・原文を確認します。対応する確定予約がある場合だけ、予約V2の既存下書きと比較し、保存コマンドへ進めます。既存下書きは無断で置き換えず、既存の公開本文も変更しません。

段階BからCへの自動化は、対応付けと競合処理の確認後に別途実装します。元の `isCompleted` を公開命令に変換しません。

### 段階D：明示的な保護者公開

職員が対象児童と本文を確認して公開します。取込、下書き保存、公開、LINE送信はそれぞれ別の状態として扱います。今回LINE送信の実装・設定・実行は行いません。

公開後に元の通信が変わった場合は、公開本文を保持したまま新しい下書き候補を作り、再確認を待ちます。

### 段階E：写真とバディの言葉

写真の実際の保存場所、権限、対象児童を確認してから設計します。今回、写真連携は未実装です。

バディの3行は本文を置き換えず、原文ハッシュに対応する別の下書きとして保持する案です。元の本文が変わったら確認済み状態を解除します。AI生成と公開を分け、職員の確認後に表示します。バディの設定・生成ルール・モデル・APIキー・料金の扱いは未決定であり、今回AI APIを呼び出しません。

## 7. 予約のない過去記録

予約V2の現行通信モデルは確定予約に依存しています。対応予約がない過去の通信は、そのままでは下書き保存・公開できません。

過去通信を表示するために架空の予約を作ると、予約・利用実績・定員等の業務データに影響します。その方法は採りません。

まず通信V2側で元の識別子と業務日を持つ履歴として保持し、後の段階で予約に依存しない過去記録の公開モデルを設計します。その場合も児童と保護者の対応、職員の事業所権限、公開の取り消し、出典と修正履歴を維持します。

## 8. 未確認・未実装の範囲

- 実環境でのデータ件数、保存形式のばらつき、既存の公開・送信状況。
- 通信と予約の児童・事業所IDの実際の対応。
- 写真の保存場所と取込可能性。
- 既存の日別記録と児童別の写しの一致状況。
- 自動取得、取込候補保存、クロスシステムの認証、同期監視。
- 過去記録の公開モデル、バディ生成、LINE送信。

上記が確認・実装されるまでは、「自動連携済み」「過去通信を移行済み」「保護者へ公開済み」とは扱いません。
